# Atlas v0.2 — Secure Project Workspace Implementation Contract

**Status:** Proposed implementation contract; not a database migration  
**Target:** One working institutional project, scoped to one or more authorized organizations  
**Release gate:** No tenant-schema DDL until the intended Supabase project and its actual schema have been inspected

## 1. Objective

Deliver one secure project workspace that can carry an accountable operational workflow:

`PLACE → PROJECT → EVIDENCE → DECISION → ACTION → VERIFIED OUTCOME`

This contract turns the v0.2 issue into a concrete implementation boundary. It is deliberately narrower than the long-term Atlas Regenerative Decision Engine.

A successful increment must prove two things at the same time:

1. An authorized institutional team can complete the workflow.
2. A user from another organization cannot read, change, infer, or export that organization's private records, even when they know record identifiers.

## 2. Preconditions and current blockers

The repository already references `organizations`, `organization_memberships` and `portfolio_observations`, but the checked-in migration set does not establish their creation. Application helpers also reference `audit_events` and `decision_links`, whose definitions were not found in the checked-in migrations inspected for this milestone.

This does **not** prove that these objects are absent from the live database. Their actual definitions, policies, grants, constraints, triggers and applied migration history must be obtained from the intended Supabase environment.

The connected Supabase account currently exposes a project marked `INACTIVE`; its identity as the Atlas Sanctum development project has not been confirmed, and live table/migration inspection could not complete.

### Stop conditions

Do not:
- create or apply project/tenant migrations against an unconfirmed Supabase project;
- assume the organization tables or role semantics from application TypeScript alone;
- backfill records to an organization based only on a user's current membership;
- convert existing user-owned water or field records into organization-owned data without an approved mapping;
- expose service-role credentials to browser code;
- treat a successful Next.js build as evidence that RLS is correct.

## 3. Separate the two authorization dimensions

Do not conflate institutional administration with workflow authority.

### Organization membership

The existing application expects organization membership roles:

| Organization role | Administrative scope |
|---|---|
| `owner` | Organization ownership and administration |
| `admin` | Organization membership and configuration |
| `member` | Ordinary organization access |
| `viewer` | Read-only organization access |

These are tenant-administration roles. Their actual live definition and permitted actions must be verified.

### Functional role

The current onboarding/database vocabulary is:

- `analyst`
- `authorizer`
- `implementer`
- `verifier`
- `steward`

These describe duties in a governed workflow, not global administrator status.

**Recommended default:** a project membership carries a scoped access level plus one assigned functional role. Organization owners/admins may manage membership but do not automatically receive authority to approve a decision or verify an outcome. A later release can add multiple functional grants per person if a real pilot requires multi-hat participation.

| Project access level | Access |
|---|---|
| `manager` | Manage project configuration and membership within organization policy |
| `contributor` | Submit and maintain permitted project records |
| `viewer` | Read permitted project material |

Functional duties:

| Functional role | Default responsibility |
|---|---|
| `analyst` | Register observations/evidence and prepare analysis |
| `authorizer` | Approve or reject a decision within assigned project scope |
| `implementer` | Record assignment and execution updates |
| `verifier` | Independently verify submitted outcomes |
| `steward` | Maintain governance quality, corrections and review discipline |

Effective permission is the intersection of authenticated identity, organization membership, project access level, functional role, record classification and requested operation.

A role displayed in the interface is never an authorization control by itself.

## 4. Proposed minimum data model

These are logical contracts to reconcile with the real schema before writing SQL. Names and types may need adjustment after reconnaissance.

### 4.1 Place and project

**`places`**

- `id`
- `organization_id` (nullable only for explicitly public/shared reference places)
- `name`, `place_type`
- `admin_level`, `admin_code` (nullable)
- `geometry` or a controlled external spatial reference (defer PostGIS until confirmed available/needed)
- `source_reference`, `observed_at`, `created_by`, `created_at`

**`projects`**

- `id`, `organization_id`
- `name`, `slug`, `purpose`, `domain`
- `status` (`draft`, `active`, `paused`, `completed`, `archived`)
- `created_by`, `created_at`, `updated_at`

**`project_places`**

- `organization_id`, `project_id`, `place_id`
- `relationship` (e.g. `operates_in`, `monitors`, `serves`)
- composite tenant-consistent foreign keys

A project may span several places. Keep an explicit relationship rather than treating a typed place name as a verified geography.

### 4.2 Project membership

**`project_memberships`**

- `organization_id`, `project_id`, `user_id`
- `access_level` (`manager`, `contributor`, `viewer`)
- `functional_role` (one of the five canonical functional roles)
- `status` (`invited`, `active`, `suspended`, `revoked`)
- `invited_by`, `created_at`, `updated_at`

Constraints:
- one active membership per project/user in the initial model;
- the project and membership must belong to the same organization;
- only an authorized manager/admin may grant or revoke membership;
- users cannot grant themselves a role or change their organization/project identifiers.

### 4.3 Evidence and source provenance

**`evidence_sources`**

- `id`, `organization_id` (nullable only for approved public sources)
- `publisher`, `source_name`, `source_uri`
- `source_type`, `license`
- `published_at`, `retrieved_at`, `collection_method`
- `created_by`, `created_at`

**`evidence_records`**

- `id`, `organization_id`, `project_id`
- `evidence_type` (`observation`, `dataset`, `document`, `measurement`, `inference`)
- `title`, `claim_or_observation`
- `source_id`, `observed_at`, `collected_at`, `recorded_at`
- `method`, `limitations`, `quality_status`
- `place_id` (nullable)
- `created_by`, `created_at`, `supersedes_id` (nullable)

Evidence is not automatically truth. Preserve the author, source, collection method, limitations, uncertainty and corrections.

### 4.4 Decision and authorization history

**`decision_records`**

- `id`, `organization_id`, `project_id`
- `title`, `problem_statement`, `options_considered`
- `recommendation`, `uncertainties`, `limitations`
- `status` (`draft`, `submitted`, `approved`, `rejected`, `superseded`)
- `version`, `proposed_by`, `created_at`, `updated_at`

Evidence references should be versioned/snapshotted so a later correction cannot silently change what an approver actually reviewed.

**`decision_events`**

- `id`, `organization_id`, `project_id`, `decision_id`
- `event_type` (`submitted`, `reviewed`, `approved`, `rejected`, `returned`, `superseded`)
- `actor_user_id`, `reason`, `decision_version`, `created_at`

### 4.5 Action and outcome

**`action_records`**

- `id`, `organization_id`, `project_id`, `decision_id`
- `description`, `owner_user_id` (nullable if assigned to a named external organization/role)
- `status` (`proposed`, `assigned`, `in_progress`, `reported_complete`, `cancelled`)
- `due_at`, `completed_at`, `created_by`, `created_at`

**`outcome_observations`**

- `id`, `organization_id`, `project_id`, `action_id`
- `indicator_code`, `value`, `unit`, `observed_at`
- `observation_note`, `verification_method`, `evidence_record_id`
- `submitted_by`, `submitted_at`
- `verification_status` (`pending`, `verified`, `rejected`)
- `verified_by`, `verified_at`, `verification_note`

**Critical distinction:** submission creates a pending observation. It must not populate `verified_by` or `verified_at`. Only a separate authorized verification operation may transition it to `verified`.

### 4.6 Audit trail

**`audit_events`**

- `id`, `organization_id`, `project_id` (nullable where appropriate)
- `actor_id`, `event_type`, `entity_type`, `entity_id`
- `payload` (allowlisted metadata only; no secrets or unnecessary personal data)
- `created_at`

Application users must not be able to update/delete audit history. Actor identity must be derived from the authenticated session or a trusted database-side operation, not accepted from client JSON.

Do not add hash-chaining as a substitute for access control or immutable backups. First establish correct event capture and restricted mutation.

## 5. Tenant integrity and database constraints

Once the actual schema is known, enforce tenant consistency in the database, not only in server code.

Recommended pattern:
- every organization-owned parent has a unique key on `(organization_id, id)`;
- every tenant-owned child stores `organization_id` and `project_id`;
- a composite foreign key `(organization_id, project_id)` references the parent project's `(organization_id, id)`;
- nested entities use composite parent references where necessary;
- prevent updates that move a record between organizations/projects;
- index membership lookup and every common tenant/project foreign key.

Do not rely on a child row's `organization_id` without validating it against its parent.

## 6. Authorization and RLS design

Before policies are written, settle the role matrix below with the product owner and pilot owner.

| Operation | Analyst | Authorizer | Implementer | Verifier | Steward | Viewer |
|---|---:|---:|---:|---:|---:|---:|
| Read permitted project | yes | yes | yes | yes | yes | yes |
| Submit evidence | yes | yes | limited | limited | yes | no |
| Review/challenge evidence | limited | limited | no | yes | yes | no |
| Draft/submit decision | yes | yes | no | limited | yes | no |
| Approve/reject decision | no | yes | no | no by default | no by default | no |
| Record action execution | no | no | yes | no | limited | no |
| Submit outcome observation | limited | no | yes | yes | limited | no |
| Mark outcome verified | no | no | no | yes | no by default | no |
| Manage memberships | no | no | no | no | no | no |

Project manager and organization owner/admin permissions are additional access-management capabilities. They do not automatically confer functional approval or verification rights.

### Separation-of-duties defaults

1. The proposer cannot approve their own decision.
2. An action implementer cannot verify their own reported outcome.
3. An outcome submitter cannot verify that same observation.
4. A project manager may manage participants but may not self-assign an approval or verification role.
5. Any exception must be explicitly authorized, recorded and visible in the audit history; do not introduce exceptions in the first increment.

### RLS requirements

- Enable RLS on all exposed tenant-owned tables.
- Scope reads and writes through organization membership and project membership.
- Use both `USING` and `WITH CHECK` for updates.
- Do not trust user-editable metadata or client-supplied actor/role fields.
- Treat RPCs, views, exports and storage paths as part of the same authorization boundary.
- Avoid recursive membership-policy evaluation. If helper functions are necessary, inspect their security mode, owner, fixed `search_path` and execute grants; keep privileged functions out of exposed schemas where possible.
- Keep the ordinary application client user-scoped. Any service-role operation must have an explicit actor/scope check and server-only credentials.

## 7. Minimum acceptance tests

Use a disposable Supabase project with synthetic identities only.

### Tenant isolation
1. Org A member can read Org A project and permitted child records.
2. Org B member cannot read Org A project by UUID.
3. Org B member cannot infer Org A evidence through nested joins, RPCs, search, counts or exports.
4. Org B cannot insert a child row referencing an Org A project.
5. A user with no active membership cannot access private project records.
6. Revoking membership removes subsequent access.

### Roles and duties
7. Viewer cannot submit evidence or mutate a project.
8. Analyst cannot approve a decision.
9. Authorizer cannot approve a decision they proposed.
10. Implementer cannot mark their own outcome verified.
11. Verifier cannot verify an outcome they submitted.
12. Organization owner/admin cannot bypass project-level restrictions or separation-of-duties rules by virtue of their admin role alone.

### Integrity and audit
13. Cross-tenant parent/child references fail at the database constraint layer.
14. Client-supplied `created_by`, `approved_by`, `verified_by` and `actor_id` are ignored or rejected.
15. Decision approval records the approved version and event timestamp.
16. An evidence correction retains the prior version and correction reason.
17. An ordinary authenticated user cannot update/delete audit history.
18. Outcome submission remains `pending`; only a designated verifier can set `verified`.

### Regression
19. Existing user-owned water-pilot and field-record access remains functional during migration.
20. Synthetic/demo records remain visibly distinct from field-verified records.

## 8. Implementation sequence

### Gate 0 — Engineering baseline
- Diagnose GitHub Actions runner/job creation failure from actual GitHub logs or runner checks.
- Verify typecheck locally/CI once dependencies can be installed and commands can execute.
- Keep unit tests running and add the smallest useful domain/API tests.

### Gate 1 — Live schema reconnaissance
- Confirm the correct Atlas development Supabase project.
- Capture tables, columns, constraints, indexes, RLS/forced-RLS, policies, grants, functions, triggers, storage policies and migration history.
- Compare the live result with checked-in migrations and document drift.

### Gate 2 — Approve authorization semantics
- Confirm the two authorization dimensions and role matrix.
- Confirm proposer/approver/verifier separation.
- Identify the institutional pilot owner and its data authority.

### Gate 3 — Project foundation
- Generate migration only after Gates 1–2 pass.
- Add project and project membership records.
- Add tenant-consistent parent/child relationships and RLS.
- Test two synthetic organizations at database and API layers.

### Gate 4 — Workflow records
- Add evidence/source registry.
- Add versioned decision records and decision events.
- Add actions and pending outcome observations.
- Add independent verification and audit history.

### Gate 5 — Pilot validation
- Demonstrate the complete workflow using labelled synthetic data.
- Obtain an authorized pilot owner to validate the workflow and the actual decision question.
- Do not call the workflow operational or validated until this happens.

## 9. Decisions still required

These items must be resolved before the first tenant migration:
- Which connected Supabase project is the Atlas Sanctum development environment?
- Does the current `organization_memberships` table use exactly `owner/admin/member/viewer`, and what are its existing RLS policies?
- Does one project membership hold one functional role in v0.2, or must users have multiple functional roles from day one?
- Can organization owners/admins also hold functional roles? (Recommended: yes, but authority remains separately granted.)
- Are project managers allowed to appoint an approver, or must the organization owner/admin approve that assignment?
- What retention and deletion rules apply to evidence and audit records?

## 10. Definition of done

The v0.2 workspace foundation is not done when a project dashboard renders. It is done when two synthetic organizations can use the same application safely, the authorized users can perform their assigned work, the evidence and decision history can be reconstructed, outcomes require an independent verifier, and the complete test suite passes in CI.
