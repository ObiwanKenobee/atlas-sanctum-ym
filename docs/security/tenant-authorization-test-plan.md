# Atlas tenant authorization test plan

**Status:** Pre-implementation test specification  
**Scope:** Organization/project isolation, role enforcement, evidence provenance and decision workflow  
**Safety:** Use a disposable Supabase development project and synthetic fixture identities. Never run destructive fixtures against production.

## 1. Current testability findings

The repository's `package.json` currently exposes only `dev`, `build` and `start`; no unit, integration, browser or database test runner is configured. Do not describe tests as passing until a runner is added and the tests are executed in CI.

The server-side Supabase client uses the publishable key and session cookies. This is appropriate for user-scoped operations when database RLS is correct. Keep service-role credentials server-only and never use them as a substitute for authorization.

## 2. Required synthetic test fixture

Create this fixture only in a disposable development database:

### Organizations
- Org A: `test-org-a`
- Org B: `test-org-b`

### Users
- Alice: Org A owner
- Ben: Org A manager
- Cara: Org A contributor
- Dana: Org A viewer
- Evan: Org B owner
- Fran: Org B contributor
- Grace: Org A reviewer/approver (if reviewer and approver are separate roles)

### Projects
- Project A1 belongs to Org A
- Project A2 belongs to Org A
- Project B1 belongs to Org B

### Records
- Evidence A1 belongs to Project A1
- Evidence B1 belongs to Project B1
- Decision A1 belongs to Project A1
- Action A1 belongs to Decision A1
- Outcome A1 belongs to Project A1 / Action A1

All IDs must be generated by the test environment. Do not copy production identifiers into fixtures.

## 3. Authorization matrix

Legend: **Allow** means the role may perform the operation within its assigned project and organization scope. **Deny** means the database/API must reject it, not merely hide the UI control.

| Operation | Owner | Admin | Manager | Contributor | Reviewer | Approver | Viewer | Other tenant |
|---|---:|---:|---:|---:|---:|---:|---:|---:|
| Read permitted project | Allow | Allow | Allow | Allow | Allow | Allow | Allow | Deny |
| Manage organization membership | Allow | Allow | Deny | Deny | Deny | Deny | Deny | Deny |
| Create project | Allow | Allow | Policy-defined | Deny | Deny | Deny | Deny | Deny |
| Submit evidence | Allow | Allow | Allow | Allow | Policy-defined | Policy-defined | Deny | Deny |
| Review/challenge evidence | Allow | Allow | Allow | Policy-defined | Allow | Allow | Deny | Deny |
| Draft decision | Allow | Allow | Allow | Policy-defined | Policy-defined | Allow | Deny | Deny |
| Approve/reject decision | Policy-defined | Policy-defined | Policy-defined | Deny | Reviewer only if explicitly delegated | Allow | Deny | Deny |
| Assign project action | Allow | Allow | Allow | Policy-defined | Deny | Policy-defined | Deny | Deny |
| Submit outcome observation | Allow | Allow | Allow | Allow | Policy-defined | Policy-defined | Deny | Deny |
| Mark outcome verified | Policy-defined | Policy-defined | Policy-defined | Deny | Allow if designated | Allow | Deny | Deny |
| Read audit history | Allow | Allow | Allow | Scoped | Scoped | Scoped | Policy-defined | Deny |
| Mutate/delete audit history | Deny | Deny | Deny | Deny | Deny | Deny | Deny | Deny |

Before coding policies, the product owner must approve the exact role matrix. In particular, decide whether owner/admin can approve their own decisions, whether the proposer can approve their own proposal, and whether reviewers may also be approvers. For consequential decisions, default to separation of proposer and approver.

## 4. RLS and API test cases

### Tenant isolation
1. Alice can select Project A1 and its permitted child records.
2. Evan cannot select Project A1 even when given its UUID.
3. Evan cannot update/delete Project A1 or any child record.
4. Alice cannot read Project B1 or Evidence B1.
5. Fran cannot infer Org A data through nested joins, views, RPCs or storage object paths.
6. A user with no membership cannot read organization or project records.
7. Revoking a membership immediately removes subsequent access.

### Parent-child integrity
8. A user cannot insert an Evidence row with Org A and a Project B1 foreign key.
9. A user cannot attach an Action in Org A to a Decision in Org B.
10. A user cannot attach an Outcome to an Action outside its project/tenant.
11. A project member cannot change a record's `organization_id` or `project_id` to move it across tenants.
12. Cascading deletes cannot erase audit history that must be retained.

### Role boundaries
13. Viewer can read permitted records but cannot submit evidence.
14. Contributor can submit evidence but cannot approve decisions.
15. Reviewer can challenge evidence but cannot grant themselves approval authority.
16. Approver can approve only within assigned project scope.
17. A proposer cannot approve their own decision unless a documented policy explicitly permits it.
18. Organization admin cannot access a project explicitly restricted from their role if the product adopts project-level isolation.

### Identity and attribution
19. Client-supplied `created_by`, `approved_by`, `actor_user_id` and role claims are ignored or rejected; actor identity comes from the authenticated session.
20. An unauthenticated request cannot create or read private records.
21. A service-role server route performs its own actor and scope checks before privileged writes.
22. Audit events record the authenticated actor and the authorized action, not arbitrary client metadata.

### Evidence and decision integrity
23. Evidence requires source, collection/observation time, method and limitation fields appropriate to its type.
24. Evidence corrections create a superseding version or correction event; prior history remains visible to authorized reviewers.
25. A decision approval captures the decision version and evidence snapshot it approved.
26. If evidence changes after approval, the system flags the decision as requiring review; it does not silently rewrite the approved basis.
27. Only authorized reviewers can mark outcomes verified.
28. A cryptographic digest or signature is never rendered as a truth/accuracy certification.

### Storage and exports
29. Private evidence files cannot be downloaded by another tenant.
30. Signed URLs expire and are issued only after project authorization.
31. CSV/JSON/decision-brief exports apply the same tenant and field-level permissions as the UI.
32. Publicly shareable evidence is explicitly classified and approved before publication.

## 5. Test layers and recommended tooling

The repository currently has no test runner. Introduce the smallest useful test stack in a dedicated change:

- **Vitest** for pure authorization helpers, validators and domain logic.
- **Supabase local development / disposable project** for SQL migrations and RLS integration tests.
- **pgTAP** (if available in the selected Supabase environment) for database-level assertions.
- **Playwright** only for a small number of end-to-end flows once the project has stable test accounts and a seeded environment.

Do not add all of these without checking the project's package manager, CI workflow and Supabase local setup. The initial mandatory gate is database-level tenant isolation.

## 6. CI gates

A pull request changing authorization, migrations or tenant-owned data must run:

1. TypeScript typecheck.
2. Lint.
3. Production build.
4. Migration apply against a clean disposable database.
5. RLS positive and negative integration tests.
6. A migration-upgrade test from the previous schema snapshot.
7. A check that no service-role key or secret is included in client bundles or repository files.

No release should pass on build success alone. Build success does not prove RLS correctness.

## 7. Migration-specific checks

For each proposed migration:

- Confirm the migration version is newer than all applied migrations.
- Confirm the target tables, columns, constraints, triggers and policies exist as expected.
- Check for orphaned child records before adding foreign keys.
- Check duplicate data before adding unique constraints.
- Backfill only records with an unambiguous organization/project owner.
- Preserve current user-owned access during the expand phase.
- Use explicit transactions where supported and safe.
- Keep a rollback/recovery plan; for data migrations, prefer reversible mapping and backup over destructive rollback.
- Run the migration against a production-like copy before release.
- Record row counts and orphan counts before/after backfill.

## 8. Release acceptance gate

Do not ship the multi-tenant increment until all of the following are true:

- The live tenant schema and all current RLS policies have been inspected.
- The role matrix has been approved by the product owner and pilot institution.
- All cross-tenant read/write tests pass at database and API layers.
- Parent-child tenant consistency is enforced.
- Existing single-user water-pilot records remain accessible to their legitimate owners.
- Audit history cannot be rewritten by application users.
- Storage and export paths are tenant-scoped.
- CI runs the tests on every relevant pull request.
- A rollback/recovery procedure has been rehearsed in a non-production environment.

## 9. What must be returned from schema reconnaissance

Run `supabase/diagnostics/tenant-schema-reconnaissance.sql` in the target Supabase project's SQL Editor. Return the result sets for:

1. Table inventory and column definitions.
2. Constraints and foreign keys.
3. RLS enabled/forced state.
4. All relevant policies.
5. Grants.
6. Indexes.
7. Membership/authorization helper functions and triggers.
8. Migration history (if the standard history relation exists).

Review and redact any project identifiers or sensitive metadata before sharing. This diagnostic does not select application row data and contains no DDL or DML.

**Stop condition:** If the existing membership table or its RLS policies cannot be understood, do not implement a new tenant policy by assumption.
